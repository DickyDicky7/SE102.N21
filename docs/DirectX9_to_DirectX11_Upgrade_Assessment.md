## 2. How Deep Are the D3D9 Dependencies?

A search of every `.cpp` and `.h` file revealed:

- **478 references** to D3D9/D3DX9 patterns across the entire codebase.
- **39 files** use D3DX math types (`D3DXVECTOR2/3`, `D3DXMATRIX`, `D3DCOLOR`, `RECT`).
- **8 call sites** to `GraphicsHelper::DrawSprite()` — the single rendering entry point.
- The rendering layer is **well-encapsulated**: ~90% of all D3D9 graphics code lives in just **two files** — `GraphicsHelper.h/.cpp` and `main.cpp`.

### The D3D9 APIs are used in several ways:

### 2.1 Fixed-Function Device Management (`main.cpp`)
- `Direct3DCreate9()` and `IDirect3DDevice9::CreateDevice()`
- `IDirect3DDevice9::Clear()`, `::Present()`, `::BeginScene()`, `::EndScene()`
- `D3DPRESENT_PARAMETERS`, `D3DCREATE_SOFTWARE_VERTEXPROCESSING`
- `D3DMULTISAMPLE_8_SAMPLES` (anti-aliasing)

### 2.2 ID3DXSprite — The Single Biggest Dependency (`GraphicsHelper.cpp`)
- `ID3DXSprite::Begin()` / `Draw()` / `End()` / `SetTransform()` — used for **all** sprite rendering.
- `D3DXMatrixTransformation2D()` — flip, scale, and rotation transforms for sprites.
- `D3DXCreateSprite()` — sprite handler creation in `LoadD3D()`.

### 2.3 D3DX Math Library (39 files — pervasive)
- `D3DXVECTOR2`, `D3DXVECTOR3` — positions, directions, camera vectors.
- `D3DXMATRIX` + `D3DXMatrixLookAtLH()`, `D3DXMatrixOrthoLH()`, `D3DXMatrixScaling()`, `D3DXMatrixIdentity()`.
- `D3DXToRadian()` — angle conversions.
- `D3DCOLOR_XRGB` — color packing.

### 2.4 D3DX Texture Loading (`GraphicsHelper.cpp`)
- `D3DXGetImageInfoFromFile()`, `D3DXCreateTextureFromFileEx()`.

### 2.5 Fixed-Function Transforms (`main.cpp` + `Camera.cpp`)
- `IDirect3DDevice9::SetTransform(D3DTS_WORLD / VIEW / PROJECTION)` — the legacy FFP transform pipeline, set directly on the device.

### 2.6 Fixed-Function Vertex Rendering (Debug Only, `GraphicsHelper.cpp`)
- Vertex buffers, `D3DPT_LINELIST`, `D3DFVF_XYZ | D3DFVF_DIFFUSE` — behind a `DRAW_BOX` flag.

## 3. Feasibility: ✅ Yes — Feasible, Moderate Effort

### Why it's doable
1. **Rendering is encapsulated** — most D3D9 graphics code is in `GraphicsHelper.h/.cpp` and `main.cpp`. Rewrite those, and most of the game keeps working.
2. **It's a 2D game** — D3D11 can render sprites as textured quads with an orthographic projection. The math is conceptually straightforward.
3. **Textures are BMP-based** — D3D11 can load these via WIC (`WICTextureLoader`) or `DirectXTK`.
4. **Game logic barely touches graphics** — it mostly calls `GraphicsHelper::DrawSprite()` with a position and angle.
5. **D3D11 ships with the Windows SDK** — the legacy DXSDK_Jun10.exe dependency can be dropped entirely (a bonus).

### What needs changing

| Area                | D3D9 Approach                                      | D3D11 Replacement                                                | Effort     |
|---------------------|----------------------------------------------------|------------------------------------------------------------------|------------|
| **Device**          | `IDirect3D9` + `IDirect3DDevice9`                  | `ID3D11Device` + `IDXGISwapChain` + `ID3D11DeviceContext`       | Medium     |
| **Sprite rendering**| `ID3DXSprite` (Begin/Draw/End)                     | Custom quad renderer: vertex buffer + shader + `DrawIndexed`     | High       |
| **Math**            | `D3DXVECTOR*`, `D3DXMATRIX`, `D3DXMatrix*`         | DirectXMath (`XMFLOAT2/3/4`, `XMMATRIX`, `XMStore*`)             | High (pervasive — 39 files) |
| **Transforms**      | `SetTransform(D3DTS_*)` FFP                        | Pass matrices to a vertex shader via constant buffers            | Medium     |
| **Textures**        | `D3DXCreateTextureFromFileEx`                      | `WICTextureLoader` or `D3D11CreateTexture2D` + SRV               | Low        |
| **Window setup**    | Win32 + `D3DPRESENT_PARAMETERS`                    | Win32 + `DXGI_SWAP_CHAIN_DESC`                                   | Low        |
| **Input**           | DirectInput 8                                      | Can stay as-is (separate API)                                    | None       |
| **Audio**           | DirectSound 8                                      | Can stay as-is (separate API)                                    | None       |

### Core Rendering Rewrite (GraphicsHelper)

The heart of the work replaces `ID3DXSprite` with a D3D11 sprite batch renderer. Conceptually:

```cpp
// D3D9: one call does everything
spriteHandler->Draw(texture, rect, &center, &position, color);

// D3D11: build a quad with position + UV coords, set vertex/index
//        buffers, set shader resources, set the transform in a
//        constant buffer, then draw
```

A D3D11 sprite renderer requires:
- A **vertex shader** that applies a world/view/proj matrix and outputs position + UV.
- A **pixel shader** that samples a 2D texture.
- A **vertex structure** with `XMFLOAT3 position` + `XMFLOAT2 texcoord`.
- An **orthographic projection matrix** (replacing `D3DXMatrixOrthoLH`).
- A simple **constant buffer** for the transform matrices.

The `DrawSprite()` signature (`SPRITE, D3DXVECTOR3, DIRECTION, FLOAT`) does **not** need to change — only its implementation.

### D3DX Math → DirectXMath: The Pervasive Change

`D3DXVECTOR3` appears in **39 files** (not just graphics files). For example:
- `Entity.h` uses `D3DXVECTOR3 position` as the base position for ALL game entities.
- `Camera.h/.cpp` uses `D3DXVECTOR3 eye / at / up` + `D3DXMATRIX viewMatrix`.
- `BossStage3Hand.h` has 7–12 D3D math references.

**Strategy:** Replace `D3DXVECTOR2/3` → `DirectX::XMFLOAT2/3` and `D3DXMATRIX` → `DirectX::XMFLOAT4X4` (or `XMMATRIX`). This is mechanical but touches many files. To minimize churn, define type aliases:

```cpp
using Vector3 = DirectX::XMFLOAT3;
using Matrix  = DirectX::XMFLOAT4X4;
```

## 5. Recommended Approach

If proceeding, structure the work as follows:

1. **Set up D3D11 basics first** — Get a blank D3D11 window compiling with a simple colored clear. This validates the toolchain (Windows SDK instead of DXSDK) and D3D11 initialization.

2. **Rewrite `GraphicsHelper` and `main.cpp`** — Replace device creation, implement a minimal D3D11 sprite renderer (quad + shader + ortho proj), swap texture loading to WIC/`DirectXTK`.

3. **Replace D3DX math** — Define aliases (`using Vector3 = DirectX::XMFLOAT3`) and do a project-wide find-and-replace. Update matrix operations to use `DirectX::XMMatrix*` functions.

4. **Port the sprite drawing** — Translate the `ID3DXSprite::Draw()` flip/rotate/transform logic from `D3DXMatrixTransformation2D()` to manual matrix math with `XMMatrixTransformation` / `XMMatrixScaling` / `XMMatrixRotation`.

5. **Test incrementally** — Get one sprite rendering correctly, then re-enable everything.

6. **Leave input/audio untouched** — DirectInput 8 and DirectSound 8 work fine alongside D3D11. Modernize those separately (e.g., XInput / GameInput, XAudio2) if needed.

## 6. Bottom Line

**Yes, it's feasible.** The upgrade is moderate difficulty: the rendering logic is centralized in `GraphicsHelper` and the game is 2D, which keeps scope manageable. The biggest challenges are:

1. **Replacing `ID3DXSprite`** with a D3D11 quad-based sprite renderer.
2. **Swapping `D3DX` math types** across 39 files to DirectXMath.

A key benefit: you'd drop the legacy DirectX SDK (DXSDK_Jun10.exe) in favor of the modern Windows SDK, which simplifies the build environment.

## 8. Outcome: What Was Actually Built

The migration is complete and verified running. The final shape differs from
the plan above in a few deliberate ways.

### Where the plan was followed

- D3D9/D3DX9 are gone. The build links only `d3d11.lib`, `d3dcompiler.lib`,
  `dxgi.lib`, `windowscodecs.lib` (plus the untouched `dinput8.lib` /
  `dxguid.lib`). The legacy DXSDK dependency is dropped.
- `DX11Math.h` provides the `D3DXVECTOR2/3` / `D3DXMATRIX` / `D3DXTo*` shim over
  DirectXMath, so the ~40 game-logic files compile unchanged. This was chosen
  over a project-wide find-and-replace, and it worked: no gameplay file was
  touched by the graphics migration.
- Texture loading goes through WIC, replacing `D3DXCreateTextureFromFileEx`.
- Input (DirectInput 8) and audio (DirectSound 8) were left on their old APIs.
- `DDSTextureLoader9.h/.cpp`, listed above as "may be unused", was confirmed
  unreferenced and deleted along with its project entries.

### Where the plan was *not* followed

- **DirectXTK was not added.** Neither `WICTextureLoader` nor `SpriteBatch`
  turned out to be necessary — WIC directly is ~60 lines, and `SpriteBatch`
  would have been a step *backwards* from the instanced renderer below.
  There is no NuGet/vcpkg dependency; the project builds from a clean checkout
  with nothing but the Windows SDK.
- **`ID3DXSprite` was not reproduced.** The plan assumed the `DrawSprite()`
  implementation could be a direct translation of the D3D9 flip/rotate logic.
  That turned out to be the single biggest trap in the migration: the D3D9 code
  pre-negated `position.x/position.y` and pre-rotated the position by `-angle`
  purely to cancel `ID3DXSprite`'s own transform back out of the translation
  (`ID3DXSprite::Draw` applies `SetTransform` to `position - center + local` as
  one unit). Translating those hacks literally into a hand-built matrix chain —
  which is what a first pass produces — makes every sprite come out mirrored
  about the world X axis and displaces rotated sprites along an arc around the
  world origin. The fix was to *delete* the compensations and compose the world
  matrix in the correct order instead.

### The pipeline as built

- **Explicit transform chain.** `SpriteVS.hlsl` walks
  LOCAL → WORLD → VIEW → CLIP one space per line. World space is Y-up in level
  units; the D3D9 build's Y-flipping world matrix and negative-height
  orthographic projection are both gone, along with the negated camera Y they
  existed to cancel.
- **Instanced sprite batching.** A static unit quad (bottom-centre anchored,
  4 vertices / 6 indices) plus a dynamic per-instance stream carrying each
  sprite's world matrix, atlas rect and tint. Batches flush on texture change,
  so a screen of terrain is a handful of `DrawIndexedInstanced` calls instead
  of one draw call per sprite. A flush binds only the things that actually
  differ between batches — the texture, and the draw itself. Input layout,
  topology, index/vertex buffers and shaders are invariant, so they are bound
  once per frame and re-bound only when the debug line pipeline has been up in
  between (`g_boundPipeline`); the instance buffer stays bound at offset 0 for
  every batch, because the ring offset rides on `StartInstanceLocation`.
- **Flip-model swap chain** (`FLIP_DISCARD`, 2 buffers) via
  `IDXGIFactory2::CreateSwapChainForHwnd`, with a bitblt `DISCARD` fallback.
- **Build-time shader compilation.** FXC compiles the four `.hlsl` files to
  `.cso` in the output directory, so a shader syntax error is a build error.
  `GraphicsHelper` loads the `.cso` and only falls back to
  `D3DCompileFromFile` if it is missing.
- **POINT sampling** — correct for NES-era pixel art, and it is also what stops
  atlas neighbours bleeding into sprite edges: a point sample reads exactly one
  texel, so it cannot average across a source-rect boundary. The CLAMP address
  mode does *not* contribute to that, despite being the intuitive reading —
  addressing clamps to the *texture's* `[0,1]` range and knows nothing about the
  sub-rect a sprite occupies. Switching `Filter` to LINEAR would therefore bleed
  neighbouring atlas cells into every sprite edge with no address mode able to
  prevent it; that change needs the source rect inset by half a texel in
  `DrawSprite`. MSAA was intentionally dropped (it only softens edges this
  artwork wants hard).
- **Single-threaded device, one queued frame.** Every D3D call is made on the
  thread running `WinMain` — the game loop directly, and `OnResize` via
  `WindowProc`, which only ever runs inside that loop's `DispatchMessage` — so
  the device is created `SINGLETHREADED` and skips its internal per-call
  locking. `SetMaximumFrameLatency(1)` caps the flip model's frame queue:
  because `dt` is a constant and every timer counts frames, each frame DXGI is
  allowed to buffer is a whole frame between sampling a key and seeing it.
- **Letterboxed viewport.** The projection is fixed to the 640×600 design
  resolution and `WM_SIZE` re-letterboxes it into the client area, so resizing
  never distorts the art or changes how much of the level is visible.
- **Debug line renderer**, restoring the D3D9 helper's `DRAW_BOX` hit-box
  overlay (`DRAW_HITBOXES` in `GraphicsHelper.cpp`). `DrawBox` takes an explicit
  rotation pivot and `DrawSprite` passes the sprite's own anchor, so a rotated
  box spins with its sprite. An earlier version rotated the absolute corner
  positions, which swept the box along an arc around the world origin — the
  same class of mistake as the `ID3DXSprite` compensations described above.
  Its shaders, input layout and vertex buffer are created only when
  `DRAW_HITBOXES` is on: built unconditionally, a missing `DebugVS.cso` *and*
  `DebugVS.hlsl` would have refused to start the game over an overlay it was
  not going to draw. `DrawBox` and `FlushDebugLines` test for the pipeline
  rather than assume it, so the public `DrawBox` stays safe either way.
- **The loop runs on a fixed 60 Hz clock.** The game's logic is a hybrid, and
  that is what makes the update rate load-bearing rather than incidental.
  Movement is per *frame* — `Motion::CalculateUniformMotion` is `c + v` with no
  `dt`, and 24 files depend on it, so every velocity is tuned in
  units-per-update. Animation frames (`HasAnimations.h`), weapon fire rates,
  the `GunBossStage1` shoot cadence, the `RifleMan` hide timers and the scene
  transitions are all on the real clock via `GetTickCount64`. The two halves
  therefore only agree at one update rate.

  The DX9 loop, and the first DX11 port, let `Present`'s vblank wait pick that
  rate — so they agreed only on a 60 Hz display, which is what the game was
  written on. On a 120 Hz panel Bill moved at double speed with a normal-speed
  run cycle, and the boss cadences drifted out of step with everything around
  them. `WinMain` now accumulates real elapsed time from
  `QueryPerformanceCounter` and runs the logic in fixed 1/60 s steps, decoupled
  from presentation: one step per frame at 60 Hz, one every other frame at
  120 Hz, two per frame at 30 Hz. Catch-up is capped at 5 steps and the backlog
  is then dropped, so a breakpoint or a dragged window is absorbed instead of
  replayed as a burst — the same failure the occlusion handling below prevents.
  Dropping it is conditional on a *whole* step still being owed: hitting the
  5-step ceiling does not by itself mean anything is pending, and zeroing the
  accumulator on the step count alone discarded the sub-step remainder, which
  made the game run steadily slow wherever five steps per iteration was normal.

  Threading a variable `dt` through the motion helpers was the alternative and
  was rejected: it would mean re-tuning every velocity in the game, and the
  frame-tuned constants scattered through the state machines would still be
  wrong afterwards.
- **Frame pacing survives an occluded window.** An occluded flip-model `Present`
  (minimised or fully covered) returns `DXGI_STATUS_OCCLUDED` *without* waiting
  for vblank, so nothing throttles the loop. `Present` reports that and `WinMain`
  sleeps instead of spinning. Once occluded, `GraphicsHelper::IsOccluded` lets
  `WinMain` skip the drawing entirely rather than build frames for `Present` to
  discard; it answers from a flag the rest of the time and only asks DXGI (via
  `Present(0, DXGI_PRESENT_TEST)`, which flips nothing and waits on nothing)
  while occlusion is actually in effect, since a swap chain becomes visible
  again without the window itself changing in any way we could observe locally.
  This mattered far more before the fixed timestep
  above, when a few seconds in the taskbar fast-forwarded spawn timers,
  animations and the boss state machines through a chunk of the level; the
  accumulator now holds the game at 60 Hz either way, and the sleep is what
  keeps the process from pinning a core meanwhile.
- **Occlusion and device loss are told apart.** `Present` returns a three-way
  `PresentResult`, not a `BOOL`. A device lost to a TDR, a driver update or an
  adapter change also stops returning `S_OK`, and folding that into "occluded"
  left the game running blind behind a frozen window — still reading input, still
  advancing every timer, never drawing again, and saying nothing to the player.
  `DeviceLost` reports the removal reason and ends the loop; `OnResize` routes a
  failed `ResizeBuffers` (or back-buffer view) into the same path, since either
  one leaves the renderer with no target and would otherwise be equally silent.
- **Failures are reported.** Device, shader, pipeline and texture creation all
  report what broke; the D3D11 debug layer is enabled in Debug builds.
